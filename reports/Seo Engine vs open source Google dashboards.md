# Fix silent truncation before copying competitors

Seo Engine does something most of the field does not: it stores daily Search Console and GA4 history and puts organic sessions on one timeline with tracked rank data. The closest rivals either read everything live, as [SailDesk](https://github.com/nykee/SailDesk) does, or store history without a documented join, as [OpenGSC](https://github.com/fenjo26/OpenGSC) does. The bigger risk is correctness, not features. Seo Engine requests **`rowLimit: 25_000` with no `startRow` pagination**, so a large site's query-level report is cut off with no warning, and the Google-facing numbers can look plausible while being incomplete. The app also shows no daily "data through" notice, and its own code comments disagree about how far back hourly data goes. The Merchant Center section already follows the supplemental-source pattern that commercial feed tools use, so it needs targeted fixes, not a redesign. In order, the fixes are: paginate or flag truncation, show data freshness, handle 429 errors, scope cache clears per project, and share one page-key rule across both sources.

## Few rivals store history, so keep the stored design

Open-source projects that combine Search Console and GA4 are few and young. Most have zero stars, so their stability is unknown. The table below shows the closest projects on storage and join method.

| Project | Stars (last push, 2026) | Storage | How it joins GSC and GA4 |
|---|---|---|---|
| Seo Engine | Local project | Daily rows in MySQL; live GSC for hourly and older ranges | GA4 organic sessions on one timeline with tracked ranks; join key not stated |
| [OpenGSC](https://github.com/fenjo26/OpenGSC) | 61 (Nov 18), MIT | Local SQLite | A GA4 property is linked to any site |
| [Ninja Analytics](https://github.com/looneyhills1-png/ninja-analytics) | 0 (Nov 16), MIT | Postgres tables per source | Not described |
| [SailDesk](https://github.com/nykee/SailDesk) | 0 (Nov 8), MIT | None; live reads | Pairs each GSC property with a GA4 property by display name |
| [QueryRank](https://github.com/AhmadFaraz-crypto/QueryRank) | 0 (Nov 2), MIT | Postgres dashboards; live streaming | Not documented |

Only OpenGSC has a long history, at 1,036 commits, and SailDesk and QueryRank have fewer than ten. SailDesk's live-only design is a poor model to copy. It **cannot show anything older than Google keeps**, and OpenGSC's 16-month preset matches that retention window ([OpenGSC](https://github.com/fenjo26/OpenGSC)). Stored history is what lets Seo Engine keep trends past that window, provided it syncs before the window closes. Commercial Looker Studio templates from [Windsor.ai](https://windsor.ai/data-studio-seo-reporting-template/) blend GSC and GA4 on date and landing page, but they keep no history of their own. No project in the notes showed a weekly or monthly grouping. Seo Engine's commit "Bring back the Granularity dropdown with Weekly and Monthly" therefore looks like a real difference, though only the commit title was read.

## Silent truncation and stale data damage trust most

The row cap is the most damaging issue. Google's Search Console API returns at most **25,000 rows per request**, and Fivetran documents a separate **50,000 rows per day** limit per property ([Fivetran KB](https://fivetran.com/docs/connectors/applications/google-search-console/troubleshooting/kb-search-console-rows-per-day-limit)). Open-source users hit both: [searchConsoleR issue #48](https://github.com/MarkEdmondson1234/searchConsoleR/issues/48) reports one day of data returning only 5,000 rows, and [issue #43](https://github.com/MarkEdmondson1234/searchConsoleR/issues/43) reports a row-limit download error. A guide on export limits also reports that a page boundary once returned one row twice and skipped another ([Schmalbach](https://www.vincentschmalbach.com/handling-search-console-export-limits-and-pagination-gaps/)). I confirmed in the code that `src/lib/providers/google.ts` sends `rowLimit: 25_000` at lines 100, 122 and 204, and that nothing in `src/lib` pages with `startRow`. The sync therefore cannot tell a complete answer from a cut one.

Freshness is the second problem. Search Console's last two to three days are routinely incomplete, and the trade press has covered several API stalls ([Search Engine Roundtable](https://www.seroundtable.com/google-search-console-api-delayed-36551.html)). Seo Engine returns `lastDataAt` only in hourly mode (`src/lib/search-console-live.ts`, line 20), so the daily view gives users no sign that recent days are provisional. The hourly window is also unclear. The comment at `search-console-live.ts` line 25 says Search Console keeps hourly data for about 10 days, while the comment at `google.ts` line 114 says only the last few days. Neither the range nor the code clamps old requests or shows an error. Google's documentation was unreachable from this research, so the true window is unverified, which is itself the reason to resolve the conflict in code.

## Page joins and quota handling need one rule each

Search Console and GA4 disagree about pages for structural reasons. Search Console groups by canonical URL, GA4 records the URL the browser loaded, and clicks and sessions are different units ([Search Engine Journal](https://www.searchenginejournal.com/ask-an-seo-why-is-ga4-reporting-higher-traffic-than-gsc/547327/)). Seo Engine does not appear to have a page-level normaliser on the join path, though the notes did not read the components and actions that perform the join. The only normalisation I found is the crawler key in `src/lib/audit/analyze.ts` (around line 25) and property matching in `src/lib/gsc-property.ts`. That audit normaliser is a good starting point, because the cheapest fix for this class of mismatch is one shared key rule for host, scheme, trailing slash and query string. The rule must not merge distinct canonical pages, and the page should say which definition each number uses.

Quota handling is half done. `google.ts` caches Google answers for five minutes in `providerCache` (lines 27 to 48), which is sound. However, a grep for `429`, `retry` and `Retry-After` in that file found nothing. Google's Merchant API quota guidance, as a search summary, advises throttling and exponential back-off, and `quota/request_rate_too_high` is the per-minute error ([Merchant API quotas](https://developers.google.com/merchant/api/guides/quotas-limits/quotas)). The `afterWrite` hook in `src/lib/actions/merchant.ts` (lines 74 to 77) deletes every `providerCache` row in the database, across all projects. That keeps data correct but spends quota for every other project after each write. Scoping the clear to the writing project's keys would avoid that cost.

## Merchant Center already follows the commercial pattern

Seo Engine's Merchant Center design matches the commercial tools. It creates one API-owned supplemental data source named after its edits, and links it first in the primary source's default rule (`src/lib/actions/merchant.ts`, lines 408 to 466). Google's Merchant API describes a supplemental source as a data source to link into one or more primary sources, and exposes create, patch and fetch calls for it ([datasources_v1](https://merchantapi.googleapis.com/$discovery/rest?version=datasources_v1)). [DataFeedWatch](https://www.datafeedwatch.com/blog/supplemental-feeds-google-merchant-center) and [Feedonomics](https://feedonomics.com/blog/using-a-supplemental-feed-vs-editing-product-details-in-google-merchant-center/) use the same join-by-ID method. Feedonomics warns that edits made directly in Merchant Center override feed values, and that attribute rules can conflict with overrides. The notes could not confirm how a supplemental source ranks against an attribute rule, so that ordering needs a test before anyone relies on it.

Seo Engine covers more of the Merchant Center surface than the commercial feed managers I could read. It handles shipping and returns, promotions writes, feed fetch control, reviews and reports, while the vendor pages show mainly feeds and product rules. Those vendor gaps are only as good as the search summaries behind them, since their pages could not be opened. The open-source options are narrower: [gmc-mcp](https://github.com/kiwoongeom/gmc-mcp) is read-heavy and serves AI assistants rather than dashboards, and [google/rubik](https://github.com/google/rubik) is archived. Seo Engine's notifications, which group account issues, product status and latest feed uploads with links back to the source, match the pattern that vendors use. Two checks remain. Channable and Shopify both warn that the move to the Merchant API can change product IDs and lose item history, a claim that is not confirmed by Google or Shopify, and Seo Engine should confirm its IDs survived the Content API sunset. The Content API sunset is reported as 18 August 2026 in a search summary that the notes did not open.

## What should change, in order

The changes below are ranked by the damage they prevent, not by effort. Each is small and local, and none requires moving away from the stored-history design.

| Priority | Change | Where | Why |
|---|---|---|---|
| 1 | Paginate GSC queries with `startRow` until a page returns fewer rows than the limit, or set a `truncated` flag | `src/lib/providers/google.ts` lines 100, 122, 204 | Silent cut-off on large sites ([Schmalbach](https://www.vincentschmalbach.com/handling-search-console-export-limits-and-pagination-gaps/), [searchConsoleR #48](https://github.com/MarkEdmondson1234/searchConsoleR/issues/48)) |
| 2 | Show "data through <date>" in daily views and avoid defaulting the end date to today | Daily dashboard views; `search-console-live.ts` | Recent days are incomplete ([Fivetran](https://fivetran.com/docs/connectors/applications/google-search-console/troubleshooting/data-missing-three-days)) |
| 3 | Resolve the conflicting hourly-window comments, then clamp or warn outside the window | `search-console-live.ts` line 25; `google.ts` line 114 | Two comments disagree; the window is unverified |
| 4 | Retry 429 responses with `Retry-After` and exponential back-off | `fetchGoogle` in `google.ts` | No handler found; Google advises back-off |
| 5 | Scope the `afterWrite` cache clear to the writing project | `src/lib/actions/merchant.ts` lines 74 to 77 | Global flush spends quota for every project |
| 6 | Share one page-key normaliser across GSC and GA4 joins | Referral sync in `sync.ts`; start from `src/lib/audit/analyze.ts` | Canonical versus loaded URLs cause most mismatches ([Search Engine Journal](https://www.searchenginejournal.com/ask-an-seo-why-is-ga4-reporting-higher-traffic-than-gsc/547327/)) |
| 7 | Test supplemental-source precedence against attribute rules and confirm product IDs after migration | `src/lib/actions/merchant.ts` lines 408 to 466 | Vendor warnings, not confirmed by Google |

Some things should not change. The stored-history design should stay, and the app should not drift toward SailDesk's live-only model, because history beyond Google's retention is a real advantage. Setup is heavier than SailDesk's, which needs no database, and Seo Engine needs Node 20.19+ and MySQL 8+. But the notes measured no setup time, so simplifying setup is not a priority until there is evidence it blocks users.

## Conclusion

The competitive question is less about which features are missing and more about whether the numbers are complete and labelled. Seo Engine's stored history, its weekly and monthly granularity and its Merchant Center coverage are differentiators that the open-source field mostly lacks. Its main exposure is numbers that look right but are not: truncated query reports, recent days shown as final, and page joins that disagree without explanation. Those are the places where a user would lose trust, and they are cheap to fix.

The evidence has limits. Google's developer documentation, including the Search Console hourly window, `dataState` semantics and the Merchant API quota figures, could not be reached, so those numbers remain unverified. Vendor claims come from search summaries, WooCommerce's channel app was not examined, and no competitor dashboard interface was inspected. The row-limit gap, the missing 429 handling and the conflicting hourly comments were checked directly in the code.
